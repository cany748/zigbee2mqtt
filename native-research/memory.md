# Память z2m: куда уходит RAM и что даёт «нативное ядро + маленький JS-движок для конвертеров»

Цель: снизить потребление оперативной памяти. Все цифры — RSS на одном стенде (Linux x86-64, Node 22.22, quickjs-ng 0.17.0, Nova `4eea7c6`), скрипты лежат в `memory-bench/`.

Сценарий «типичная установка»: загружены ядро z2m + zigbee-herdsman + zigbee-herdsman-converters и 5 популярных модулей устройств (tuya, philips, lumi, sonoff, ikea — **1501 определение**). Это ближе к худшему случаю: z2m грузит модуль производителя целиком, даже если из него нужно одно устройство.

## 1. Где память в Node сейчас

| Состояние | RSS, МБ | JS heap, МБ |
|---|---|---|
| Пустой Node | 42 | 3 |
| + herdsman | 77 | 9 |
| + converters (только ядро, без устройств) + контроллер z2m | 118–122 | 21–27 |
| + 5 модулей устройств (1501 определение) | 145 | 55 |
| + все 4405 определений | 173 | 77 |

Стоимость модулей устройств (прирост heap): tuya 10 МБ, philips 5.7, lumi 2.4, sonoff 2.2, ikea 1.2 и т. д.

**JS heap — лишь треть RSS.** Остальное — накладные расходы V8/Node: young generation (по умолчанию semi-space 16 МБ → `new` = 32 МБ), байткод/код, рантайм Node.

## 2. Сравнение движков на одном и том же коде

| Что загружено | Node | Node + флаги¹ | QuickJS (исходник) | QuickJS (байткод, `qjsc -ss`) |
|---|---|---|---|---|
| Пустой движок | 42 | — | 3.3 | 3.3 |
| Только ядро converters + ZCL | 69 | 64 | — | **10.7** |
| Converters + 1501 определение | 112 | 91 | 58 | **44** |
| **Весь JS: z2m + herdsman + converters + 1501 определение**² | 146 | 101 | 78 | **51** |
| То же после 200 тыс. вызовов `fromZigbee` | 138 (рост +26) | 91 | — | **43** (рост +0.7) |

¹ `--max-semi-space-size=1 --lite-mode`.
² mqtt, ws и winston заменены заглушками: в обсуждаемой архитектуре они нативные.

Скорость конвертеров: QuickJS — 756 мс на 200 тыс. сообщений (~3.8 мкс на сообщение), V8 — 191 мс. Для Zigbee (десятки сообщений в секунду) это несущественно.

**Nova** (`trynova/nova`): Test262 — 40 515 из 50 733 (~80%), 52 краша. На бандле конвертеров падает при разборе: регулярные выражения с lookahead (`(?!UTC)`) не поддерживаются. Пик RSS до падения — 75 МБ. Авторы прямо пишут, что код с `any`/`unknown` у них «медленнее и тяжелее» — а конвертеры почти целиком такие. Сейчас для этой задачи непригодна.

## 3. Главный вывод из замеров

В QuickJS z2m + herdsman добавляют к одним конвертерам **всего ~7 МБ** (51 против 44 МБ). Основная память — это **данные определений устройств** (~33 МБ на 1501 определение в QuickJS, ~11 МБ heap / ~43 МБ RSS в V8), а не код herdsman/z2m.

Отсюда:

- Переписывание herdsman (84 тыс. строк: ember 21k, ezsp 9.5k, z-stack 8.3k, deconz/zigate/zboss ~9k, ZCL/ZDO spec 26k, контроллер 7k) и z2m (13k) на нативный язык экономит порядка **5–10 МБ** по сравнению с запуском того же кода в QuickJS. Цена — несколько человеко-лет и вечная синхронизация с upstream.
- Граница «нативное ядро ↔ конвертеры» широкая. Из конвертеров вызываются `getEndpoint` (~1530 мест), `read` (642), `write` (377), `command` (194), `configureReporting` (172), `save` (133), `bind`, `getClusterAttributeValue` и др.; используются `device.meta`, `globalStore` (322), колбэки `customReadResponse`, таймеры (45), `Buffer` (332), `onEvent`/`configure`. Плюс расширения z2m (`homeassistant`, `bridge`, `publish`, `receive`, `otaUpdate`, `groups`) работают с `definition.exposes/toZigbee/fromZigbee/options` напрямую — их тоже пришлось бы либо оставить в JS, либо гонять всё через мост.
- ZCL-спецификация нужна обеим сторонам: нативной — для разбора кадров, JS — конвертерам (`Zcl.*` импортируется в 92 файлах). Получается дублирование или ещё один мост.

## 4. Варианты и оценка

| Вариант | RSS (1501 определение) | Трудоёмкость |
|---|---|---|
| Node как сейчас | ~145 | — |
| **A.** Node + флаги V8 (`NODE_OPTIONS="--max-semi-space-size=1 --lite-mode"`) | **~96–101** | минуты; нужно проверить CPU на слабых устройствах (`--lite-mode` выключает оптимизирующий JIT) |
| **B.** A + поштучная ленивая загрузка определений вместо целых модулей производителя | **~73** + единицы МБ на реально используемые устройства | средняя: изменение в zigbee-herdsman-converters (генерация «фабрик» определений / разбиение модулей) |
| **C.** Весь существующий JS на QuickJS + нативный I/O (serial, TCP, MQTT, WS, HTTP, fs, таймеры) как модули рантайма | **~51** + нативный I/O (оценка 5–10) ≈ 55–60; с ленивыми определениями ≈ 25–30 | большая, но без переписывания логики: слой совместимости с нужной частью Node API + байткод `qjsc` |
| **D.** Предложенная: нативный herdsman/z2m/I/O + QuickJS только для конвертеров | ~44 (QuickJS) + нативное ядро (оценка 10–15) ≈ 55–60; с ленивыми определениями ≈ 25–30 | очень большая: переписать ~100 тыс. строк и спроектировать мост для API выше |

Оценки «нативный I/O» и «нативное ядро» — экспертные, не измерены. Остальные цифры измерены.

## 5. Рекомендация

1. Сразу: **A** — флаги V8. Минус ~35% без изменений кода.
2. Затем: **B** — ленивые определения устройств. Это главный источник памяти при любом движке, и он нужен в любом из вариантов C/D.
3. Если после A+B памяти всё ещё мало (например, Pi Zero / роутеры): **C**, а не D. C даёт ту же память, что и D, но сохраняет весь существующий код, upstream-совместимость и внешние конвертеры/расширения. Внешний JS в C работает естественно, в D — только через мост. Нативной частью в C становятся только транспорты (serialport без N-API, MQTT-клиент, WS/HTTP-сервер), то есть именно то, что в D и так пришлось бы писать.
4. Движок: **quickjs-ng**. Nova пока не готова.

Чего замеры не покрывают: реальная работа с координатором и десятками устройств (состояние устройств, база, очереди); поведение GC QuickJS (подсчёт ссылок + сборщик циклов) на длинной дистанции; CPU на ARM. Это следующий шаг, если выбрать C.

**Нерабочие:**
- Nova: регулярные выражения с lookahead не поддерживаются (`(?!UTC)`, `(?=[A-Z])`). После замены этих двух мест — `ReferenceError: Uninitialized this binding` (баг с производными классами).
- Boa: загрузка — 249 МБ, на нагрузке `RuntimeLimitError: reached the maximum stack size`.

**Не тестировались:**
- SpiderMonkey, GraalJS: прямые загрузки с mozilla.org/oracle закрыты на стенде, а сборка из исходников слишком тяжела.
- Duktape, MuJS, mJS, Elk: только ES5 — пришлось бы транспилировать классы, async и генераторы в ES5 через Babel + regenerator; это отдельный эксперимент.
- txiki.js, LLRT: рантаймы поверх QuickJS(-ng), по движку эквивалентны строкам QuickJS выше.

### Выводы по движкам

- **Hermes с заранее скомпилированным байткодом** — лучший баланс: минимум анонимной памяти (30 МБ), скорость конвертеров на уровне V8 (280 мс против 213), быстрый старт (байткод отображается в память из файла). Минусы: компилятор `hermesc` нужен на этапе сборки (из исходника сам Hermes ест 170–260 МБ); нет `Proxy` по умолчанию и нет `with`/локального `eval`; движок ориентирован на React Native, встраивание с Node-подобным I/O придётся делать самим.
- **quickjs-ng с байткодом** — почти та же память (42.5 МБ, анонимной 37), в ~3 раза медленнее Hermes, зато самый простой для встраивания (один C-файл, есть готовые рантаймы txiki.js/LLRT) и с полным ES2023+.
- **Escargot** — 50 МБ без всякой предкомпиляции; хорош, если нужен разбор исходника на лету (например, для внешних конвертеров).
- **JerryScript** — рекордно мало памяти (18 МБ на 1501 определение), но загрузка 60 с и ~5 мс на сообщение — для z2m непригоден.
- V8 (Node/Deno) и JSC (Bun) — 90–170 МБ; Deno и Bun по памяти не лучше Node. `bun --smol` эффекта не даёт.
- Относительно Node + флаги (91 МБ), переход конвертеров на Hermes/QuickJS-байткод экономит **~50 МБ**, на Escargot — **~40 МБ**.
