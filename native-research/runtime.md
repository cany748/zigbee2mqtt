# Замена Node.js для z2m: Node vs Bun vs Deno (+ LLRT), с разными параметрами и байткодом

Что мерялось: **полный z2m** (текущий `dist/`), а не отдельные конвертеры. Координатор заменён фейковым `Controller` из тестового набора z2m (`test/mocks/zigbeeHerdsman.ts`, 62 устройства реальных моделей + 9 групп). Включены Home Assistant discovery, фронтенд (HTTP + WebSocket) и availability. Подключение к настоящему MQTT-брокеру (aedes). Поток 50 ZCL-отчётов в секунду (`genOnOff`, `genLevelCtrl`, температура, влажность, батарея) в течение 90 с; RSS снимается каждую секунду. Стенд: `runtime-bench/` (`fake-run.cjs`, `matrix.py`, `longrun.py`, `cpu.py`).

Версии: Node 22.22.0 (V8 12.4), Node 24.21.0, Bun 1.3.14 (JSC), Deno 2.9.6 (V8 15.0), LLRT 0.9.0-beta (QuickJS).

## 1. Может ли рантайм заменить Node прямо сейчас

| Проверка | Node 22 | Bun 1.3.14 | Deno 2.9.6 | LLRT 0.9 |
|---|---|---|---|---|
| Полный старт z2m (фейковый координатор) | ✅ | ✅ без правок | ✅ с `--unstable-detect-cjs` | ❌ |
| MQTT, HA discovery, публикация состояний | ✅ | ✅ | ✅ | — |
| Фронтенд: HTTP + WebSocket API | ✅ | ✅ | ✅ | ❌ нет модуля `http` |
| Реальный herdsman, ember-адаптер по TCP | ✅ | ✅ | ✅ | — |
| **Последовательный порт** (`@serialport/bindings-cpp`, N-API) | ✅ | ❌ **крэш**: аддон вызывает `uv_default_loop`, Bun это не поддерживает (`unsupported_uv_function`) | ❌ `Bad file descriptor (os error 9)` при записи: fd, открытый аддоном, Deno не умеет использовать через `node:fs` | ❌ N-API нет |
| Внешние конвертеры/расширения (JS в рантайме) | ✅ | ✅ (тот же механизм `import()`) | ✅ | — |

Проверка serial: pty-пара, эхо на master-стороне, `SerialPort` из herdsman на slave-стороне (`compat/serial-test.cjs`). Это ровно тот путь, которым идут адаптеры ember/ezsp/zstack/deconz/zigate/zboss.

**Вывод:** без доработок Node можно заменить только для установок с **сетевым (TCP) координатором** — и Bun, и Deno запускают z2m полностью. Для USB/UART-координаторов (большинство установок) **ни Bun, ни Deno сегодня не работают**: нужно заменить `@serialport/bindings-cpp` на реализацию через FFI (`bun:ffi` / `Deno.dlopen` + `termios`) или нативный модуль рантайма. LLRT — не замена: нет `http`, `tls`, `worker_threads`, части `fs`/`util`/`process` (`shims/llrt-polyfill.cjs` — начало списка), падает на загрузке `stream`.

## 4. Выводы

1. **Bun** запускает z2m без правок, но: (а) **не работает с serial-координаторами** (N-API аддон serialport → крэш), (б) по памяти **хуже Node на 45%** (229 против 158 МБ), (в) тратит **в 3.7 раза больше CPU** в простое-с-нагрузкой. Байткод Bun (`--bytecode`, `--compile --bytecode`) память **увеличивает** (+20…60 МБ): кэш байткода JSC держится в анонимной памяти. Единственный режим, где Bun догоняет Node по памяти, — `BUN_JSC_useJIT=0`, но он съедает 2 ядра CPU. `--smol` и `forceRAMSize` почти не влияют.
2. **Deno** запускает z2m (нужен `--unstable-detect-cjs`), по памяти близок к Node (163 против 158 МБ по умолчанию; 146 с флагами), но **serial не работает** (fd из N-API аддона непригоден для `node:fs`).
3. **Node остаётся лучшим вариантом**, а главный выигрыш — во флагах V8:
   `NODE_OPTIONS="--max-semi-space-size=1 --optimize-for-size --no-opt --no-maglev"` → **124 МБ вместо 158 (−22%), без роста за 5 минут**, ценой +35% CPU (9.0 против 6.7 с за 5 минут — это 3% одного ядра). Совместимо с WebAssembly, т. е. со всем z2m.
4. **Node 24 по умолчанию потребляет 240–260 МБ** — в 1.6 раза больше Node 22. Причина — увеличенный по умолчанию young generation: `--max-semi-space-size=1` возвращает его к 155 МБ, а полный набор флагов — к 127 МБ. Это важно для будущего обновления z2m на Node 24/26.
5. Единый бандл (esbuild) и код-кэш (`NODE_COMPILE_CACHE`) память **увеличивают** (+10…30 МБ): движок держит большой исходник / кэш, а ленивая загрузка модулей устройств теряется.
6. **LLRT** (QuickJS + Rust-реализации Node API) — потенциально самый лёгкий путь «QuickJS вместо V8 без переписывания z2m», но сегодня это не замена Node: не хватает `http`, `tls`, `worker_threads`, частей `fs`/`util`/`process`, N-API.
